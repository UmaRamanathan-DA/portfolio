LoanTap Credit Risk Scoring System

Predicts whether a loan applicant is likely to Fully Pay or Charge Off (default), then wraps that probability into risk scores, repayment odds, and approve/reject-style recommendations for credit analysts.

I used Lovable to rapidly prototype an explainable credit-decision UX, and separately built a working logistic-regression risk model + API on historical loan data (~396k records, ~77% accuracy / ~80% AUC). The UI is currently a clickable prototype; the model is a functioning backend. Next step: wiring them so the UI is driven by real scores.

Problem Statement

LoanTap-style consumer lending generates high application volume, but manual credit review is slow and inconsistent. Analysts need a repeatable way to score new applicants against patterns learned from historical loan outcomes — not gut feel alone.

The core question this system answers: given an applicant’s profile (amount, term, rate, grade, income, DTI, credit history, purpose, etc.), how likely are they to default? That default probability is then translated into operational outputs analysts can act on — a 0–100 risk score, repayment odds, and tiered recommendations such as APPROVE, APPROVE_WITH_CONDITIONS, REVIEW_MANUAL, or REJECT.

Bottom line: An offline-trained logistic regression credit-default model for LoanTap-style applications. Training used ~396k historical loans; live use only scores new applications and does not update the model from API or UI users.

The Solution

The project has two complementary layers. First, a classical ML scoring engine (Python, scikit-learn, FastAPI, Streamlit): logistic regression trained once on historical loan records, saved as .joblib artifacts, and deployed for inference-only scoring. Second, a Lovable AI UX prototype that shows how analysts could interact with risk outputs in a polished loan-review workflow — upload data, see flags, and explain decisions to stakeholders.

The ML backend is not generative AI. It is supervised binary classification — Fully Paid vs Charged Off — with rule-based recommendation thresholds applied on top of the predicted default probability.

ML & AI Approach CLASSICAL ML

  • Algorithm: Logistic regression (scikit-learn)
  • Training: Offline, one-time fit on historical loan CSV via train_model.py
  • Reported performance: ~77% accuracy, ~80% ROC AUC
  • Deployment: FastAPI + Streamlit app loads saved models/loan_risk_model.joblib and models/preprocessor.joblib — inference only, no retraining at runtime
  • Not used: Generative AI, LLMs, or continuous online learning from live applicants

Training vs live scoring

Phase What happens
Training (train_model.py) Fits the model once on the historical CSV (input dataset/logistic_regression.csv). ~396,030 loan records split ~80/20 train/validation (~316k / ~79k). Predictions are not written back into the training set.
Serving (API / Streamlit UI) Does not retrain. New applications are scored with the frozen model. There is no fixed user capacity at inference — it can score one application, a batch, or a whole CSV; throughput depends on the host machine.

Pipeline: Input → Output

Training path (offline, run once)

Historical CSV → Preprocess → Train logistic regression → Saved model + preprocessor (.joblib)

Runtime path (every new application)

New application (JSON / UI / CSV) → Validate → Preprocess → Predict → Risk score / approve / repay outputs

1. Training input

CSV of past loans with fields such as loan amount, term, interest rate, grade, income, debt-to-income (DTI), credit history, purpose, address, and the label loan_status (Fully Paid / Charged Off).

2. Preprocessing

  • Fill missing values
  • Engineer features — credit history years, high-DTI flags, term/grade/purpose risk flags, income/loan buckets, and related derived signals
  • Label-encode categoricals and scale numerics
  • → ~35 model features fed to logistic regression

3. Model training

  • Binary target: Fully Paid = 0, Charged Off = 1
  • Artifacts saved to models/loan_risk_model.joblib and models/preprocessor.joblib

4. Runtime input (one applicant)

Same application fields as training (loan amount, term, income, DTI, grade, etc.) submitted via API or Streamlit — without loan_status, since that is the outcome being predicted.

5. Runtime outputs (one probability, multiple wrappers)

The core output is a default probability. Different endpoints and UI views format that same score for different analyst tasks. Recommendations are threshold rules on default probability (e.g. risk score < 30 → APPROVE) — not a separate approval model.

Endpoint / view Output
Default risk Prediction (0/1), default probability, risk score (0–100), recommendation (APPROVE / APPROVE_WITH_CONDITIONS / REVIEW_MANUAL / REJECT), confidence
Repayment Repayment probability, default probability, risk category (Low / Med / High)
Approval Approval/rejection probabilities, recommendation, rule-based risk factor tags (e.g. high DTI, low income)
Batch / CSV List of the above per row, plus summary counts

What the Model Learns

Logistic regression was chosen for its balance of accuracy and interpretability — important for regulated lending decisions. Key signal groups in the ~35-feature set include:

  • Interest rate and loan grade: Higher rates and lower grades correlate with elevated default risk
  • Credit utilization and DTI: High revolving credit use and debt-to-income ratios signal repayment strain
  • Employment and income: Job tenure and verified income reduce default likelihood
  • Loan characteristics: Term length (36 vs 60 months), purpose (e.g. debt consolidation patterns), and home ownership status
  • Application details: Individual vs joint applications, verification status, and payment method

Validated with an ~80/20 train/validation split; reported metrics are ~77% accuracy and ~80% ROC AUC on held-out data.

Why Explainability Matters

Because the core model is logistic regression — not a black-box deep learner — coefficients and engineered features support clearer reasoning about which factors drive each risk score. The approval view adds rule-based risk factor tags (e.g. high DTI, low income) on top of the default probability. That transparency:

  • Builds analyst confidence in ML-assisted recommendations
  • Supports fair-lending documentation and stakeholder review
  • Enables clearer customer conversations about approval conditions
  • Keeps recommendations auditable — thresholds are explicit rules, not opaque model stacks

Business Impact

  • Faster decisions: Streamlined workflows cut review time, enabling higher application throughput
  • Lower credit losses: Better risk detection reduces defaults and charge-offs by identifying high-risk patterns in applicant profiles
  • Stronger adoption: An intuitive interface made the ML technology accessible to non-technical users from day one
  • Consistent risk assessment: Standardized scoring reduces analyst variability and improves portfolio quality

Key Insights from the Data

Analysis of the ~396k-record training set showed debt consolidation loans comprise a large share of applications, with interest rate and credit grade among the strongest default predictors. Borrowers with verified income, individual (non-joint) applications, and 36-month terms tended to show better repayment performance — patterns reflected in the engineered feature set.
